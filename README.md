# market-price — スーパーの値段メモ

いつも行くスーパーの値段を覚えておいて、**その値段が高いのか安いのか**を
その場で判断するための、個人用のアプリです。

答えたいのは次の 2 つです。

1. **たまに行った別のスーパーの値段、近所と比べて高い?安い?**
   よく行く店に「いつもの店」の印を付けておくと、その店の記録が
   比較の基準(相場)になります。旅先のスーパーで牛乳が 268 円だったとき、
   「いつもの店の相場は 198 円だから、これは 35% 高い」と教えてくれます。

2. **同じ店でも日によって値段が動く。今日の値段はいつもより高い?安い?**
   同じ店・同じ商品の過去の記録から相場を出して比べます。
   「この店のふだんは 198 円。今日の 158 円は 20% 安い」のように出ます。

値段を入力すると、**保存する前に**判定が出ます。
レジに並ぶ前に「買うかどうか」を決められるようにするためです。

## できること

| やりたいこと | どこで |
| --- | --- |
| 値段を記録する(その場で高い/安いの判定が出る) | 記録タブ |
| 商品ごとの相場・最安の店を見る | 商品タブ |
| 商品の値動きをグラフで見る | 商品タブ → 商品を選ぶ |
| 店を登録し「いつもの店」の印を付ける | 店タブ |
| 2 つの店をまるごと比べる | 比較タブ |
| 記録を振り返る・打ち間違いを消す | 履歴タブ |

そのほか、こまかい配慮:

- **税込に揃えて比べる。** 日本のスーパーは本体価格と税込価格の表示が
  混ざっています。値札の数字はそのまま入れて「税込かどうか」だけ選べば、
  比べるときは自動で税込に揃えます(税率は商品ごとに設定)。
- **内容量が違っても比べられる。** 商品に内容量(1000ml、500g、6個など)を
  登録しておくと、100ml あたり・1個あたりの単価で比べられます。
  「500ml で 128 円」と「1000ml で 238 円」のどちらが得かが分かります。
- **特売は相場から外す。** 特売を混ぜると「ふだんの値段」が実際より安く見えて、
  通常価格がいつも「高い」と判定されてしまうためです。
- **ホーム画面に追加できる**(PWA)。スマホで全画面のアプリとして使えます。

## 高い・安いをどう判断しているか

判定のしくみはすべて [`lib/priceStats.ts`](lib/priceStats.ts) にあります。
ここが間違っていると全部の画面が嘘をつくので、
[`lib/priceStats.test.ts`](lib/priceStats.test.ts) でテストしてあります。

### 相場(ふだんの値段)の出し方

- **中央値**を使います(平均ではありません)。
  桁を間違えて 9800 円と記録してしまっても、相場が引きずられないようにするため。
- **特売の記録は外します。** 通常価格の記録が 1 件も無いときだけ、
  やむを得ず特売から相場を出し、画面に断り書きを出します。

### 高い・安いのしきい値

相場から何 % 離れているかで 5 段階に分けます。

| 相場との差 | 判定 |
| --- | --- |
| −15% 以下 | かなり安い |
| −15% 〜 −5% | 安い |
| −5% 〜 +5% | ふつう |
| +5% 〜 +15% | 高い |
| +15% 以上 | かなり高い |

同じ商品でも日によって数 % は普通に動くので、
**±5% までは「ふつう」**として騒がないようにしています。

記録が 3 件に満たないうちは「記録が少ないので目安です」と添えます。
1 件だけの記録から断定しないためです。

### 2 種類の比較

| 関数 | 何と比べるか | 何が分かるか |
| --- | --- | --- |
| `judgeAgainstRegularStores` | **いつもの店**の相場 | よその店が近所より高いか安いか |
| `judgeAgainstOwnHistory` | **同じ店**の過去の相場 | いつもより高いか安いか |

`judgeAgainstRegularStores` は「いつもの店」の印が付いた店の記録だけを
基準にします。たまにしか行かない店の値段に相場が引っぱられないようにするためです。
いま見ている店自身も基準から外します(自分と比べても意味が無いので)。

## 使いはじめの手順

1. **店タブ**で、よく行くスーパーを登録します。
   「いつもの店(近所でよく行く)」に必ずチェックを入れてください。
   ここに印が付いた店の記録が、あとで比較の基準になります。
2. **商品タブ**で、値段を追いかけたい商品を登録します。
   内容量(`1000ml`、`500g`、`6個` など)を入れておくと、
   容量の違う商品どうしでも単価で比べられます。
3. **記録タブ**で、買い物のたびに値段を入れます。

判定が出るのは記録がたまってからです。
はじめのうちは「比べられる過去の記録がまだありません」と出ますが、
同じ商品を 2〜3 回記録すれば相場が出はじめます。

## 開発環境の準備

### 1. Supabase プロジェクトを作る

1. [Supabase](https://supabase.com/) でプロジェクトを作ります。
2. **Authentication → Providers** で Google と GitHub を有効にします。
3. **Authentication → URL Configuration** の Redirect URLs に、
   `http://localhost:3000/auth/callback` と本番の
   `https://<あなたのドメイン>/auth/callback` を登録します。

### 2. 環境変数

`.env.example` を `.env.local` にコピーして値を埋めます。
値は Supabase の **Project Settings → API** にあります。

```bash
cp .env.example .env.local
```

```
NEXT_PUBLIC_SUPABASE_URL=https://<your-project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<your-anon-key>
```

環境変数が無くてもビルドは通ります(その場合はセットアップ案内の画面が出ます)。

### 3. DB を作る

`supabase/migrations/` の SQL を適用します。手元で試すだけなら、
Supabase ダッシュボードの **SQL Editor** に貼って実行するのが手軽です。
マイグレーションは何度実行しても壊れません(冪等)。

### 4. 起動

```bash
npm install
npm run dev
```

### よく使うコマンド

```bash
npm run dev    # 開発サーバー
npm run lint   # 書き方のチェック
npm test       # ユニットテスト(lib/ の計算ロジック)
npm run build  # 本番と同じビルド。型エラーもここで出る
npm run icons  # PWA のアイコン・スプラッシュ画像を作り直す
```

## DB マイグレーションの運用

`main` に `supabase/` 配下の変更をプッシュすると、
GitHub Actions(`.github/workflows/supabase-migrations.yml`)が
本番 DB に未適用のマイグレーションを流します。

そのために、GitHub の **Settings → Secrets and variables → Actions** に
次の 3 つを登録してください。

| シークレット | 取得場所 |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | https://supabase.com/dashboard/account/tokens |
| `SUPABASE_DB_PASSWORD` | Supabase ダッシュボード → Settings → Database |
| `SUPABASE_PROJECT_REF` | ダッシュボードの URL に含まれる 20 文字の ref |

### マイグレーションを書くときの決まり

- ファイル名は `<タイムスタンプ>_<内容>.sql`(例: `20260906120000_phase1_initial_schema.sql`)
- **何度実行しても同じ結果になるように書く**
  (`create table if not exists` / `drop policy if exists` → `create policy`)
- **データを消す変更は入れない**(`drop table` / `truncate` / `delete` は使わない)。
  本番には実際の買い物の記録が入っています。
- 新しいテーブルには必ず RLS を付ける。値段の記録は完全に本人専用です。

## 設計のメモ

### なぜ判定を DB ではなくアプリ側でやるのか

しきい値(何 % で「安い」と言うか)は、使っているうちに
変えたくなる類のものです。DB のビューや関数に埋めてしまうと、
変えるたびにマイグレーションが要ります。

そこで **DB には生の記録だけを置き、解釈はすべて `lib/` のコードでやる**
方針にしました。しきい値を変えたいときは
`lib/priceStats.ts` の `VERDICT_THRESHOLD_PERCENT` を書き換えるだけで済みます。

### テーブルは 3 つだけ

| テーブル | 役割 |
| --- | --- |
| `stores` | 店。`is_regular` が「いつもの店」の印 |
| `products` | 商品。内容量と消費税率を持つ |
| `price_logs` | 「いつ・どの店で・その商品がいくらだったか」の 1 行 |

`price_logs` には
`(product_id, store_id, recorded_on, is_sale)` のユニーク制約があります。
同じ値札を二度打ちしても記録が二重にならず、相場が狂わないようにするためです
(アプリ側は upsert で書き込み、あれば上書きします)。
特売と通常価格は同じ日に並ぶことがあるので、`is_sale` は制約に含めて別扱いにしています。

### ライブラリの分担

| ファイル | 役割 |
| --- | --- |
| `lib/priceStats.ts` | 相場の算出と高い/安いの判定(このアプリの心臓部) |
| `lib/unitPrice.ts` | 税込への正規化・単価の計算・表示の整形 |
| `lib/storeCompare.ts` | 2 つの店のまるごと比較 |
| `lib/date.ts` | 日付まわり(YYYY-MM-DD をローカル日付として扱う) |

`lib/` の計算ロジックにはすべてユニットテストがあります(`npm test`)。
画面の見た目のテストは、手間の割に壊れやすいので入れていません。
